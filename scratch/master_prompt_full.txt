# MASTER PROMPT: ออกแบบและพัฒนา System Administration & Configuration สำหรับระบบ Zakat Management System (ZMS)

คุณคือ Senior System Analyst, Solution Architect, Senior Full-Stack Developer และ Enterprise UI/UX Designer

รับผิดชอบการออกแบบและพัฒนาระบบ **การตั้งค่าและบริหารระบบ (System Administration & Configuration)** ของ Zakat Management System (ZMS) สำหรับมูลนิธิซะกาตและสาธารณกุศล

เป้าหมายคือสร้างศูนย์กลางการบริหารระบบที่เป็นระเบียบ ใช้งานง่าย มีความปลอดภัย ลดความซ้ำซ้อน และสามารถควบคุมการตั้งค่าของทุกโมดูลได้จากจุดเดียว

# PART 1: เป้าหมายและหลักการออกแบบ

## 1.1 เป้าหมายหลัก

พัฒนาเมนูการตั้งค่าและบริหารระบบให้เป็นศูนย์กลาง (Centralized Administration) ประกอบด้วย 2 กลุ่มหลัก

**กลุ่มที่ 1: การบริหารระบบ (System Administration)**

1. จัดการผู้ใช้งาน
2. บทบาทและสิทธิ์การเข้าถึง
3. โครงสร้างองค์กรและหน่วยงาน

**กลุ่มที่ 2: การตั้งค่าข้อมูลพื้นฐาน (Master Data Configuration)**

1. รูปแบบการช่วยเหลือ
2. ประเภทความช่วยเหลือ
3. หมวดหมู่ผู้มีสิทธิ์รับซะกาต (อัสนัฟ)
4. การตั้งค่าทั่วไป

## 1.2 หลักการสำคัญ: Single Source of Truth

ต้องตรวจสอบระบบเดิมก่อนว่าแต่ละฟังก์ชันมีอยู่ที่ใดบ้าง

ตัวอย่าง:

- จัดการผู้ใช้งาน อาจมีอยู่ในเมนูผู้ดูแลระบบ
- บทบาทและสิทธิ์ อาจกระจายอยู่ในหน้าจัดการผู้ใช้งาน
- สาขาและแผนก อาจมีการตั้งค่าอยู่ในหลายโมดูล
- ประเภทความช่วยเหลือ อาจมีการกำหนดแยกในหน้าบันทึกการช่วยเหลือ
- อัสนัฟ อาจถูกกำหนดซ้ำในหน้าประเมินสิทธิ์และการเงิน
- รูปแบบการช่วยเหลือ อาจมีข้อมูลซ้ำในระบบคำร้องและระบบติดตามผล

ให้รวบรวมการตั้งค่าเหล่านี้มาอยู่ในศูนย์กลางเดียว

**กฎสำคัญ:**
- ข้อมูลประเภทเดียวกันต้องมีแหล่งข้อมูลหลักเพียงแห่งเดียว
- ห้ามสร้างตารางหรือ API ซ้ำโดยไม่จำเป็น
- เมนูอื่นต้องเรียกใช้ข้อมูลจากแหล่งข้อมูลกลาง
- หากมีการแก้ไขข้อมูลจากศูนย์กลาง ทุกโมดูลที่เกี่ยวข้องต้องใช้ข้อมูลล่าสุด
- ห้ามให้ผู้ใช้แก้ไข Master Data ซ้ำจากหลายตำแหน่ง
- การแสดงข้อมูลในโมดูลอื่นยังทำได้ แต่การบริหารจัดการต้องอยู่ที่จุดเดียว

ฟังก์ชัน:

- เพิ่มผู้ใช้งาน

- แก้ไขข้อมูล
- กำหนดบทบาท

- กำหนดสาขาและแผนก
- ระงับบัญชี
- เปิดใช้งานบัญชี
- รีเซ็ตรหัสผ่านตามสิทธิ์
- ดูประวัติการใช้งาน

- ค้นหาชื่อ

- กรองตามแผนก

## 3.2 บทบาทและสิทธิ์การเข้าถึง (Roles & Permissions)

ออกแบบระบบ RBAC (Role-Based Access Control) ที่ยืดหยุ่นและตรวจสอบได้

### การจัดการบทบาท

รองรับ:

- เพิ่มบทบาท
- แก้ไขบทบาท
- คัดลอกบทบาท
- เปิดใช้งาน
- ปิดใช้งาน
- กำหนดรายละเอียดบทบาท
- กำหนดสิทธิ์ตามโมดูล

ตัวอย่างบทบาทเริ่มต้น:

1. Super Admin
2. Admin
3. ผู้จัดการสาขา
4. เจ้าหน้าที่ทะเบียน
5. เจ้าหน้าที่ตรวจสอบและประเมินสิทธิ์
6. เจ้าหน้าที่พิจารณาอนุมัติ
7. เจ้าหน้าที่ช่วยเหลือ
8. เจ้าหน้าที่ติดตามผล
9. เจ้าหน้าที่การเงิน
10. เหรัญญิก
11. ผู้ตรวจสอบ
12. ผู้ใช้งานทั่วไป

รายการเหล่านี้เป็นบทบาทตั้งต้น ต้องสามารถเพิ่มบทบาทใหม่ได้

### การกำหนดสิทธิ์

ออกแบบ Permission Matrix แยกตามโมดูลและการกระทำ

สิทธิ์พื้นฐาน:

- Access: เข้าใช้งาน
- View: ดูข้อมูล
- Create: เพิ่มข้อมูล
- Edit: แก้ไขข้อมูล
- Delete: ลบหรือดำเนินการตามนโยบาย
- Approve: อนุมัติ
- Reject: ไม่อนุมัติ
- Export: ส่งออก
- Print: พิมพ์
- Assign: มอบหมาย
- Manage: จัดการการตั้งค่า

ตัวอย่าง Permission Matrix:

| โมดูล | View | Create | Edit | Approve | Export | Manage |
|---|---|---|---|---|---|---|
| ทะเบียนผู้มีสิทธิ์ | ✓ | ✓ | ✓ | - | ✓ | - |
| ยื่นคำร้อง | ✓ | ✓ | ✓ | - | ✓ | - |
| ตรวจสอบสิทธิ์ | ✓ | ✓ | ✓ | ✓ | ✓ | - |
| พิจารณาอนุมัติ | ✓ | - | - | ✓ | ✓ | - |
| บันทึกการช่วยเหลือ | ✓ | ✓ | ✓ | - | ✓ | - |
| ติดตามผล | ✓ | ✓ | ✓ | - | ✓ | - |
| การเงินและบัญชี | ✓ | ✓ | ✓ | ✓ | ✓ | - |
| รายงาน | ✓ | - | - | - | ✓ | - |
| การตั้งค่าและบริหารระบบ | ✓ | ✓ | ✓ | - | - | ✓ |

ตารางนี้เป็นตัวอย่างเท่านั้น ให้ตรวจสอบโมดูลและ API จริงก่อนกำหนดสิทธิ์

### การกำหนดสิทธิ์รายบุคคล

รองรับการ Override สิทธิ์รายบุคคล:

- Inherit: ใช้สิทธิ์ตามบทบาท
- Allow: อนุญาตเพิ่มเติม
- Deny: ปฏิเสธสิทธิ์

แสดงข้อมูล:

- สิทธิ์จากบทบาท
- สิทธิ์ที่กำหนดเฉพาะบุคคล
- Effective Permission หรือสิทธิ์ที่ใช้งานจริง

หากมีสิทธิ์ Deny ให้เป็นไปตามนโยบายความปลอดภัยที่กำหนดไว้

### ขอบเขตข้อมูล (Data Scope)

รองรับ:

- OWN: ข้อมูลที่ตนเองรับผิดชอบ
- DEPARTMENT: ข้อมูลภายในแผนก
- BRANCH: ข้อมูลภายในสาขา
- ORGANIZATION: ข้อมูลทั้งองค์กร

ต้องตรวจสอบขอบเขตข้อมูลจาก Backend ทุกครั้ง ห้ามพึ่งพาการซ่อนปุ่มบน Frontend เพียงอย่างเดียว

### ความปลอดภัย

- Deny by Default
- ป้องกันการเพิ่มสิทธิ์ให้ตนเอง
- ป้องกันการปิดบัญชี Super Admin คนสุดท้าย
- ตรวจสอบสิทธิ์ทุก API
- บันทึก Audit Log เมื่อมีการเปลี่ยนแปลงสิทธิ์
- ป้องกันการเข้าถึงข้อมูลข้ามสาขาโดยไม่ได้รับอนุญาต

# PART 4: การตั้งค่าข้อมูลพื้นฐาน (Master Data Configuration)

ส่วนนี้เป็นศูนย์กลางจัดการข้อมูลอ้างอิงที่ทุกโมดูลใช้ร่วมกัน

## 4.1 รูปแบบการช่วยเหลือ (Assistance Models)

กำหนดรูปแบบหรือแนวทางการช่วยเหลือของมูลนิธิ

ตัวอย่าง:

- ช่วยเหลือเป็นเงิน
- ช่วยเหลือเป็นสิ่งของ
- ช่วยเหลือด้านที่อยู่อาศัย
- ช่วยเหลือด้านอาชีพ
- ช่วยเหลือด้านการศึกษา
- ช่วยเหลือด้านสาธารณูปโภค
- ช่วยเหลือฉุกเฉิน
- ช่วยเหลือด้านมนุษยธรรม

รายการนี้เป็นตัวอย่าง ให้ตรวจสอบข้อมูลจริงที่มีอยู่ก่อน

### ข้อมูลที่ต้องกำหนด

- รหัสรูปแบบการช่วยเหลือ
- ชื่อรูปแบบการช่วยเหลือ
- คำอธิบาย
- วิธีดำเนินการ
- ต้องระบุจำนวนเงินหรือไม่
- ต้องแนบหลักฐานหรือไม่
- ต้องติดตามผลหรือไม่
- จำนวนครั้งขั้นต่ำในการติดตามผล
- ระยะเวลาติดตามผล
- สถานะเปิดใช้งาน

### การเชื่อมโยง

รูปแบบการช่วยเหลือต้องสามารถเชื่อมโยงกับประเภทความช่วยเหลือได้

ตัวอย่าง:

รูปแบบ: ช่วยเหลือด้านที่อยู่อาศัย

ประเภท:
- ซ่อมแซมบ้าน
- สร้างบ้าน
- ปรับปรุงที่อยู่อาศัย

ห้ามสร้างรายการประเภทความช่วยเหลือซ้ำในหลายโมดูล

## 4.2 ประเภทความช่วยเหลือ (Assistance Types)

เป็นการกำหนดประเภทของความช่วยเหลือที่เจ้าหน้าที่เลือกเมื่อยื่นคำร้องและบันทึกการช่วยเหลือ

ตัวอย่าง:

- ปัจจัยยังชีพ
- ซ่อมแซมบ้าน
- สร้างบ้าน
- ต่อยอดอาชีพ
- ทุนการศึกษา
- ช่วยเหลือฉุกเฉิน
- ช่วยเหลือผู้ประสบภัย
- ช่วยเหลือค่ารักษาพยาบาล

### ข้อมูลที่ต้องกำหนด

- รหัสประเภท
- ชื่อประเภท
- รูปแบบการช่วยเหลือ
- รายละเอียด
- อัสนัฟที่เกี่ยวข้อง
- กองทุนที่เกี่ยวข้อง
- เอกสารที่ต้องใช้
- วงเงินขั้นต่ำ/สูงสุด (ถ้ามีนโยบาย)
- ต้องมีการติดตามผลหรือไม่
- จำนวนครั้งขั้นต่ำในการติดตามผล
- ระยะเวลาติดตามผล
- ลำดับการแสดงผล
- สถานะเปิดใช้งาน

### การเชื่อมโยงข้อมูล

ประเภทความช่วยเหลือหนึ่งประเภทอาจรองรับหลายอัสนัฟหรือหลายกองทุนได้ตามนโยบาย

ต้องตรวจสอบความสัมพันธ์จากข้อมูลจริงและไม่กำหนดความสัมพันธ์แบบตายตัวโดยไม่มีเหตุผล

### ตัวอย่างการกำหนด

| รูปแบบการช่วยเหลือ | ประเภทความช่วยเหลือ |
|---|---|
| ด้านปัจจัยยังชีพ | ช่วยเหลือค่าครองชีพ |
| ด้านที่อยู่อาศัย | ซ่อมแซมบ้าน |
| ด้านที่อยู่อาศัย | สร้างบ้าน |
| ด้านอาชีพ | สนับสนุนทุนประกอบอาชีพ |
| ด้านการศึกษา | ทุนการศึกษา |
| ด้านฉุกเฉิน | ช่วยเหลือผู้ประสบภัย |

## 4.3 หมวดหมู่ผู้มีสิทธิ์รับซะกาต (Asnaf Management)

ออกแบบระบบจัดการหมวดหมู่อัสนัฟตามหลักการบริหารซะกาตของมูลนิธิ

ข้อมูลตั้งต้นที่ต้องรองรับ:

1. ฟะกีร (ผู้ยากไร้)
2. มิสกีน (ผู้ขัดสน)
3. อามิลีน (เจ้าหน้าที่จัดเก็บและบริหารซะกาต)
4. มุอัลลัฟ (ผู้ที่ควรได้รับการสนับสนุน)
5. อัลฆอริมีน (ผู้มีหนี้สินตามหลักเกณฑ์)
6. ฟีสะบีลิลลาฮ์
7. อิบนุสสะบีล (ผู้เดินทางที่ขัดสน)
8. หมวดอื่นที่มูลนิธิกำหนดตามหลักเกณฑ์และการอนุมัติ

### ข้อมูลที่ต้องกำหนด

- รหัส Asnaf
- ชื่อภาษาไทย
- ชื่อภาษาอาหรับ (ถ้ามี)
- ชื่อภาษาอังกฤษ
- คำอธิบาย
- หลักเกณฑ์เบื้องต้น
- เอกสารประกอบ
- รูปแบบการช่วยเหลือที่อนุญาต
- ประเภทความช่วยเหลือที่สัมพันธ์
- ลำดับการแสดงผล
- สถานะใช้งาน

### การจัดการกองทุน

หากระบบเดิมมีการจัดการกองทุนหรือการจัดสรรงบประมาณตามอัสนัฟอยู่แล้ว ให้เชื่อมโยงกับข้อมูล Asnaf กลาง

ห้ามสร้างระบบจัดสรรงบประมาณซ้ำในเมนูนี้

เมนูนี้มีหน้าที่บริหารข้อมูลหมวดหมู่อัสนัฟเท่านั้น ส่วนการจัดสรรงบประมาณให้คงอยู่ในระบบการเงินและบัญชีตามหน้าที่เดิม

### ข้อกำหนดสำคัญ

- รองรับการเพิ่มและแก้ไขข้อมูล
- ไม่ลบ Asnaf ที่มีธุรกรรมหรือประวัติอ้างอิง
- การปิดใช้งานต้องไม่กระทบข้อมูลย้อนหลัง
- การเปลี่ยนชื่อไม่ควรทำให้ข้อมูลเก่าสูญหาย
- การเปลี่ยนแปลงสำคัญต้องบันทึก Audit Log

# PART 5: การรวมศูนย์และย้ายฟังก์ชันที่ซ้ำซ้อน

ส่วนนี้สำคัญที่สุดของงาน

ก่อนพัฒนา ให้ทำ System Audit เพื่อค้นหาฟังก์ชันการตั้งค่าที่มีอยู่ในเมนูอื่นทั้งหมด

ตัวอย่าง:

| ฟังก์ชัน | ตำแหน่งที่พบเดิม | ตำแหน่งศูนย์กลางใหม่ |
|---|---|---|
| จัดการผู้ใช้งาน | เมนูผู้ดูแลระบบ | การบริหารระบบ > จัดการผู้ใช้งาน |
| จัดการบทบาท | หน้าผู้ใช้งาน | การบริหารระบบ > บทบาทและสิทธิ์ |
| จัดการสาขา | หน้าข้อมูลสาขา | การบริหารระบบ > โครงสร้างองค์กร |
| รูปแบบการช่วยเหลือ | หน้าบันทึกการช่วยเหลือ | การตั้งค่าข้อมูลพื้นฐาน |
| ประเภทความช่วยเหลือ | หน้าคำร้อง | การตั้งค่าข้อมูลพื้นฐาน |
| อัสนัฟ | หน้าประเมินสิทธิ์ | การตั้งค่าข้อมูลพื้นฐาน |
| การตั้งค่าทั่วไป | หลายตำแหน่ง | การตั้งค่าทั่วไป |

ตารางนี้เป็นแนวทาง ให้ตรวจสอบตำแหน่งจริงจาก Codebase ก่อนย้าย

## กฎการย้ายระบบ

1. ย้ายเฉพาะส่วนบริหารจัดการและการตั้งค่า
2. คงการใช้งานข้อมูลในโมดูลหลักตามเดิม
3. เปลี่ยนทุกโมดูลให้ดึงข้อมูลจาก Master Data กลาง
4. ไม่สร้างตารางข้อมูลซ้ำ
5. ไม่สร้าง API ซ้ำ
6. ไม่ทำให้ข้อมูลเก่าสูญหาย
7. ไม่เปลี่ยนรหัสอ้างอิงของข้อมูลเดิมโดยไม่จำเป็น
8. ไม่ทำลาย Foreign Key
9. หากต้อง Migration ให้สร้าง Migration ที่ปลอดภัยและย้อนกลับได้
10. หากเมนูเดิมมีฟังก์ชันตั้งค่าซ้ำ ให้เปลี่ยนเป็นการแสดงข้อมูลหรือ Link ไปยังหน้าตั้งค่ากลาง

**ตัวอย่าง:** เมื่อเจ้าหน้าที่แก้ไขชื่อประเภทความช่วยเหลือจากเมนูตั้งค่าข้อมูลพื้นฐาน ระบบยื่นคำร้อง ระบบบันทึกการช่วยเหลือ และระบบติดตามผล ต้องอ่านข้อมูลจากแหล่งกลางเดียวกัน

# PART 7: สถาปัตยกรรมและฐานข้อมูล

ก่อนพัฒนาให้ตรวจสอบเทคโนโลยีและโครงสร้างที่ใช้งานจริง

ห้ามสมมติว่า Stack หรือ Schema เป็นไปตามเอกสารนี้ทั้งหมด

แนวทาง:

- ใช้ Frontend และ Backend เดิม
- ใช้ API เดิมเมื่อเหมาะสม
- ใช้ Prisma Schema เดิมเมื่อสามารถต่อยอดได้
- ใช้ PostgreSQL หากเป็นฐานข้อมูลที่ระบบเชื่อมต่ออยู่
- แยก Master Data ออกจาก Transaction Data
- ใช้ Foreign Key
- ใช้ Unique Constraint สำหรับรหัสข้อมูล
- ใช้ Soft Delete หรือ Inactive Status สำหรับข้อมูลที่ถูกใช้งานแล้ว
- บันทึก createdAt, updatedAt, createdBy, updatedBy
- บันทึก Audit Log
- ตรวจสอบ Permission ที่ Backend

## ความสัมพันธ์ข้อมูลที่ควรรองรับ

- User → Role
- User → Organization / Branch / Department
- Role → Permission
- Assistance Model → Assistance Type
- Assistance Type → Asnaf / Fund ตามความสัมพันธ์ที่ระบบรองรับ
- Asnaf → ข้อมูลการประเมินและคำร้อง
- Master Data → Transaction ที่เกี่ยวข้อง

ต้องออกแบบความสัมพันธ์จากข้อมูลจริง ไม่สร้างความสัมพันธ์ที่ทำให้ระบบซับซ้อนโดยไม่จำเป็น

# PART 10: Acceptance Criteria

งานจะถือว่าสำเร็จเมื่อ:

1. มีเมนูการตั้งค่าและบริหารระบบเป็นศูนย์กลาง
2. แยกการบริหารระบบและการตั้งค่าข้อมูลพื้นฐานชัดเจน
3. จัดการผู้ใช้งานได้จริง
4. จัดการบทบาทและสิทธิ์ได้จริง
5. จัดการโครงสร้างองค์กรได้จริง
6. จัดการรูปแบบการช่วยเหลือได้จริง
7. จัดการประเภทความช่วยเหลือได้จริง
8. จัดการอัสนัฟได้จริง
9. จัดการการตั้งค่าทั่วไปได้จริง
10. ไม่มีหน้าตั้งค่าซ้ำซ้อนในโมดูลอื่น
11. ทุกโมดูลใช้ Master Data จากแหล่งกลาง
12. ข้อมูลเดิมยังคงอยู่ครบถ้วน
13. ระบบหลักยังทำงานได้ตามปกติ
14. Permission และ Audit Log ทำงานจริง
15. ไม่มี Mock Data ในการใช้งานจริง
